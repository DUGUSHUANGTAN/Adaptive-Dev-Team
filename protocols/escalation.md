# Escalation Protocol

When a builder encounters an issue that cannot be resolved through their own efforts, they must escalate through the proper chain. Escalation is not a failure — it's a quality mechanism.

## Escalation Chain

The escalation path follows this order:

1. **Builder → Builder Lead** (first level)
2. **Builder Lead → Architect/Planner** (second level)
3. **Architect/Planner → Leader** (third level)
4. **Leader → User** (final level, only when absolutely necessary)

Each level should attempt resolution before escalating further.

## When to Stop Guessing and Escalate

A builder must stop guessing and escalate when any of the following occur:

### Requirement Conflict
When requirements contradict each other or are unclear, don't guess — escalate.

### Architecture Conflict
When the architecture has conflicts or doesn't support the task, escalate.

### Missing Dependency
When required dependencies are missing or unavailable, escalate.

### Ownership Conflict
When ownership of work is unclear or conflicting, escalate.

### Breaking Change
When a change would break existing functionality, escalate.

### Unexpected Scope Expansion
When the task scope grows unexpectedly, escalate.

### Security Concern
When security issues are found, escalate immediately.

### Critical Uncertainty
When there's significant uncertainty about the approach, escalate.

## Escalation Rules

- Escalate early — don't wait until failure
- Provide complete context when escalating
- Don't attempt to resolve conflicts alone
- Document escalation decisions
- Follow up on escalated items
- Escalation is not failure — it's quality control

## Escalation Documentation

When escalating, include:
- What the issue is
- Why it's a problem
- What attempts have been made
- What is needed to resolve
- Impact if not resolved
